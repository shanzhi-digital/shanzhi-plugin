# 三流核对

把银行流水、发票和合同节点对上：导入 → 看哪些没对上 → 给出匹配建议 → 用户确认后执行。

## 什么时候用

- 用户给了银行对账单、收付款流水或发票明细的 Excel（.xlsx、.xls），要导入或对账。
- 用户想看还有哪些流水没匹配、想把某些流水关联到合同。
- 只看未匹配流水、不导入新文件：从第 3 步开始。

## 开始前

- 需要已连接履约系统账户。任何工具返回 kind 为 `contract-sure-auth-required` 时：把 message 原样转告用户，停下等用户回复「继续」，不要重试或绕过。
- **不要自己读 Excel 内容、不要逐行手算**。Excel 一律交给 `contract_manage_flow` 的 `action="import_excel"`，由系统解析和自动匹配。

## 第 1 步：确认要导入什么

弄清两件事，不清楚就问用户：

1. 文件路径（只收 .xlsx、.xls，不超过 20MB）。
2. 流水类型 `txnType`：
   - 1 = 发票明细
   - 2 = 收款流水
   - 3 = 付款流水
   - 0 = 收支混在一起的银行对账单，让系统按方向自动判断

## 第 2 步：导入前确认（写入）

导入会把流水写进履约系统并触发自动匹配，**必须先确认**。这样问用户：

```
准备导入：
- 文件：xxx.xlsx
- 类型：收款流水（txnType=2）
导入后系统会自动匹配合同节点。同一份流水请不要重复导入。确认导入吗？
```

用户明确回复「确认」「导入」后，调用 `contract_manage_flow`：`action="import_excel"`、`filePath`、`txnType`。

看返回：`parsedCount`（解析出多少条）、`matchedCount`（自动匹配上多少条）、`status`。把这三个数告诉用户。`parsedCount` 为 0 时，提醒用户检查表头和类型是否选对，不要继续往下做。

## 第 3 步：列出没匹配上的流水

调用 `contract_manage_flow`：`action="list_unmatched"`，只看某一类时加 `txnType`。每页默认 50 条，最多 200 条。

- 先根据 `total` 和 `summary` 说概况：共多少条未匹配、大概多少金额。
- `hasMore` 为 true 时用 `offset` 等于返回的 `nextOffset` 取下一页。用户要全部明细时才逐页翻完。
- 未匹配很多（超过 20 条）时，先按金额从大到小挑 20 条做建议，其余告诉用户还剩多少、要不要继续。

## 第 4 步：给出匹配建议

对每条要处理的流水，找候选合同和节点：

1. **找合同**：流水上有「合同编号」时，用 `contract_query`（`mode="list"`，`keyword` 填合同编号）；没有就用「对方户名」去搜，全称搜不到再试去掉「有限公司」等后缀的核心名称。
2. **方向要对**：收款流水只配销售合同（`contractType=1`），付款流水只配采购合同（`contractType=2`）；发票两种都可能，看是我方开出还是收到。
3. **找节点**：对候选合同用 `contract_query`（`mode="detail"`）查节点，比较金额和日期：
   - 节点未收金额 = `nodeAmount` − `receiptAmount`（空按 0）；
   - 节点应收日期 = `computedDate`，没有就用 `plannedDate`。
4. **定把握程度**，规则见 `references/matching-rules.md`，分高、中、低三档，每条写清依据。

每查一份合同详情，回合末尾会多一张原件卡片，一批建议里查详情的合同控制在 20 份以内。

## 第 5 步：等用户逐条确认（必须停下）

按这个格式给出建议，然后**停下来等用户确认**：

```
| 序号 | 流水ID | 日期 | 金额（元） | 对方户名 | 摘要 | 建议合同（ID / 编号 / 名称） | 建议节点（ID / 名称） | 把握 | 依据 |

请告诉我要执行哪几条，例如「执行 1、3、5」。没有把握的可以先不动。
```

确认规则：

- 用户要明确指出执行哪几条：序号列表，或「把握为高的那 N 条」这种能唯一确定范围的说法。「都行」「你看着办」不算确认，要追问。
- 把握为「低」的条目，即使用户说「全部」，也要单独再确认一次。
- 用户修改了某条的合同或节点，按修改后的执行，并在执行前复述一遍。

## 第 6 步：执行匹配（写入）

对确认过的每一条，调用 `contract_manage_flow`：`action="manual_match"`、`transactionId`、`contractId`，知道节点时加 `nodeId`。

- 一条一条执行，每条的结果都记下来。
- 某条报错就停下，把已经成功的和失败的分别告诉用户，问用户怎么处理，不要自动重试或换一份合同硬配。
- 全部执行完，再调用一次 `action="list_unmatched"`，告诉用户还剩多少条未匹配。

## 常见问题

| 现象 | 处理 |
|---|---|
| 一条流水对应好几个节点（合并付款） | 系统一次只能关联一个合同节点。告诉用户这种情况，建议关联到金额最接近、最早到期的节点，或在履约系统里手工拆分 |
| 一个节点分好几笔付（分期到账） | 每笔都可以关联到同一个节点，节点的已收金额会累加 |
| 找不到任何候选合同 | 列为「无候选」，说明可能是合同还没录入、对方户名和合同上的名称不一致，建议先录入合同（「导入并分析合同」skill） |
| 用户给的是 PDF 回单或图片 | 这个 skill 只处理 Excel。单张收款凭证可以作为节点凭证上传（`action="upload_node_evidence"`，`docType=3`），同样要先确认 |
